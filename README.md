# Negentropy UI

> neg·entropy (.n) - negative entropy  
> | denying disorder,  
> | staving off entropy or disintegration,  
> | √dhṛ (धृ) in Sanskrit,  
> modern system(s) to shape agentic behavior away from drift and divergence.

A SvelteKit component library generated through the Vercel ui-sdk (`@ui-sdk/core` + `@ui-sdk/svelte`) package. The ui-sdk supplies tested keyboard, focus, selection, dismissal and ARIA behavior; Negentropy adds a token-driven theme on top. Wrappers forward every prop to the ui-sdk part and add classes and variant props. Agents work under a paradigm of "a component and its documentation are one." No component is done until its docs page is real, complete and renders. A script gate enforces that on every build. The documentation is the proof of the component.

This current, first iteration of the components is generated by Qwen 3.8 Max and Flash. Iteration was has been a basic test run of the SDK, and I am now going through each component code, annotations, etc. The orchestrating model was instructed - 

"Here is a Vercel SDK, with the packages [@ui-sdk/core](https://github.com/vercel-labs/ui/tree/main/packages/core) and [@ui-sdk/svelte](https://github.com/vercel-labs/ui/tree/main/packages/svelte). Create the complete components library for Sveltekit that they yield, call it Negentropy UI..." + instructions for parallel documentation per component. 

- 54 components across 9 categories
- Svelte 5 runes, SvelteKit 2, Tailwind CSS v4, TypeScript 5.9
- Zero runtime dependencies beyond the ui-sdk pair and two class-merging helpers
- SSR and prerender friendly; right-to-left and keyboard support come from the core

## Quickstart

```bash
pnpm install
pnpm dev        # docs site on http://localhost:5173
```

Open the site and start at **Getting started** (`/docs/getting-started`). The sidebar lists the guides and every component.

## Scripts

| Script | What it does |
| --- | --- |
| `pnpm dev` | Run the docs site in development. |
| `pnpm build` | Production build; prerenders every docs route. |
| `pnpm preview` | Serve the production build locally. |
| `pnpm check` | `svelte-kit sync` + `svelte-check` (types and Svelte diagnostics). |
| `pnpm registry` | Regenerate `src/lib/registry.json` from every `meta.json`. |
| `pnpm new` | Scaffold a new component folder + docs page from the template. |
| `pnpm validate` | Structural proof: every component has code + complete docs. |
| `pnpm smoke` | Runtime proof: boot the build and fetch every docs page. |
| `pnpm proof` | The full gate: registry → check → validate → build → smoke. |

## The Proof Pipeline

`pnpm proof` is the definition of done. Each step must exit `0`:

1. registry — collect all `meta.json` into `src/lib/registry.json`.
2. check*— `svelte-check` reports `0 errors and 0 warnings`.
3. validate — every component has a barrel, a docs page with the six required sections and at least three live demos, and no filler markers.
4. build — the production build prerenders every route cleanly.
5. smoke — boots `vite preview` and fetches each docs page over HTTP, asserting it returns `200` and actually contains the rendered sections, demos and live ui-sdk markup (`data-slot`). Structure checks alone cannot prove a page renders.

## Documentation

Every component page at `src/routes/docs/<slug>/+page.svelte` contains six sections, each wrapped in `<Section id="…">` (which renders `data-section="…"`):

1. `installation` — import from `$lib/components/<slug>`; note the ui-sdk entry it wraps.
2. `usage` — the basic composition.
3. `demos` — at least three live, interactive `<Demo>` blocks, each showing its source.
4. `variants` — the variant/size/state matrix (never empty).
5. `api` — a `PropsTable` per part, read from the real ui-sdk types.
6. `accessibility` — the keyboard model and ARIA, from the ui-sdk docs.

Library-level guides live alongside the components:

- `/docs` — documentation overview
- `/docs/getting-started` — install, run, first component
- `/docs/theming` — semantic tokens, dark/light, customization
- `/docs/patterns` — parts, class merging, snippets, controlled state, data attributes

## Architecture

```
src/
  app.css                     # design tokens (@theme inline + --n-* variables)
  lib/
    components/<slug>/        # one folder per component
      meta.json               # registry metadata (name, slug, category, parts, entry)
      index.ts                # barrel: every wrapper part + re-exported types
      <slug>.svelte           # Root wrapper
      <slug>-<part>.svelte    # one wrapper per ui-sdk part
    docs/                     # PageHeader, Section, Demo, CodeBlock, PropsTable
    utils/                    # cn (clsx + tailwind-merge), defineVariants
    registry.json             # generated — do not edit by hand
  routes/
    +layout.svelte            # top bar, theme toggle, sidebar (guides + components)
    +page.svelte              # home / catalog
    docs/                     # guide pages + one page per component
scripts/                      # build-registry, new-component, validate, smoke
```

Each wrapper is typed with ui-sdk's `PartProps<Tag, State, Own>` intersected with the component's options. It destructures only its variant props and `class`, then spreads `...rest` onto the ui-sdk part so every HTML attribute, callback and `render`/`children` snippet passes through. Controlled roots declare `value` / `open` / `checked` with `$bindable()` and forward with `bind:`.

State is styled from **data attributes** (`data-open`, `data-checked`, `data-selected`, `data-disabled`, `data-highlighted`, …), never from JavaScript and never from an invented `data-state`. See `/docs/patterns`.

## Theming

Wrappers use semantic utilities (`bg-surface`, `text-fg`, `border-line`, `bg-accent`, `outline-ring`, …) that map through Tailwind v4's `@theme inline` to `--n-*` CSS variables. Dark is the default; `[data-theme="light"]` flips the same variables, so every component works in both themes. Recolor the whole library by overriding a handful of variables. See `/docs/theming`.

## Adding a component

```bash
pnpm new <slug>     # scaffold folder + docs page from the template
```

Then follow `RULES.md` (the agent contract): copy the canonical shape from `button`, `tabs` and `dialog`, read the ui-sdk API docs for the component, write the wrappers and the six-section docs page, and run `pnpm validate <slug>`. The orchestrator runs `pnpm proof` centrally. A component is not done until its docs
page renders.

## Notes

- A few components are `@experimental` upstream in the ui-sdk (label, rating, segmented-control, timeline, waterfall) but are marked `stable` here per the library contract. `waterfall` is a time-axis trace treegrid, not a masonry layout.
- The build may emit a benign Rollup warning about unused imports inside the upstream `@ui-sdk/svelte` package; it is not Negentropy code and not an error.
